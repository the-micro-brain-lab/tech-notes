Worker, Durable Object và WebSocket chạy thế nào

Ai chạy code của bạn, chạy lúc nào, có bao nhiêu bản, dữ liệu nằm ở đâu, và một tin WebSocket đi qua những chỗ nào. Mỗi bài có ví dụ code; bài 4 đến bài 7 có mô phỏng bấm qua từng bước.

Bài 1Bức tranh tổng

Một request trong hệ thống game đi qua tối đa năm chỗ. Hiểu mỗi chỗ làm gì là hiểu gần hết phần còn lại.

Trình duyệt
Chạy UI, gửi request HTTP và mở WebSocket.
Edge
Máy chủ Cloudflare gần người dùng nhất. Nhận kết nối, so URL với route để biết giao cho Worker nào, và giữ kết nối WebSocket kể cả khi phòng đang ngủ.
Worker
Code không trạng thái, chạy cho từng request. Cùng lúc có thể có nhiều bản (isolate) ở nhiều máy.
Durable Object
Một object có tên. Mỗi tên có đúng một bản trên toàn thế giới, và bản đó xử lý từng event một.
Storage
SQLite riêng của từng Durable Object, nằm cùng máy với nó. Còn mãi cho tới khi bạn xóa.
Ví von dùng suốt bài

Worker là quầy lễ tân của một tòa nhà: nhiều nhân viên trực cùng lúc, ai rảnh thì tiếp khách, và không ai nhớ khách hôm qua. Một nhân viên có thể vừa chờ điện thoại cho khách này vừa ghi phiếu cho khách khác.

Mỗi Durable Object là một phòng họp có đúng một thư ký. Khách của phòng nào cũng phải xếp hàng gặp đúng thư ký phòng đó. Thư ký có trí nhớ ngắn hạn (RAM) và một tủ hồ sơ (storage). Phòng vắng thì thư ký đi ngủ và quên sạch những gì trong đầu, nhưng tủ hồ sơ còn nguyên.

Các đường dây WebSocket cắm ở tổng đài dưới sảnh (edge), nên không đứt khi thư ký ngủ. Chuông reo thì thư ký dậy. Tổng đài có máy trả lời tự động cho câu "còn đó không?" (ping), nên không phải đánh thức ai.

Hai câu cần nhớ
  1. Worker: nhiều bản, không nhớ gì, một bản phục vụ nhiều request cùng lúc.
  2. Durable Object: mỗi tên đúng một bản, xử lý lần lượt, nhớ lâu bằng storage.

Bài 2Worker

Định nghĩa

Worker là một module JavaScript (hoặc TypeScript, Python, Wasm) mà Cloudflare chạy trên mạng edge mỗi khi có event, thường là một request HTTP. Bạn không thuê server và không quản lý tiến trình. Bạn chỉ export các handler; runtime gọi chúng khi có việc.

Isolate thay vì container

Code của bạn chạy trong một V8 isolate: một vùng cách ly nhẹ bên trong một tiến trình runtime đã chạy sẵn. Một tiến trình runtime chứa hàng trăm tới hàng nghìn isolate của nhiều khách hàng và chuyển qua lại giữa chúng. Theo docs, một isolate khởi động nhanh hơn khoảng một trăm lần so với một tiến trình Node trong container hay VM, và tốn ít bộ nhớ hơn cỡ một bậc.

Cột Lambda là kiến thức chung để so sánh, không lấy từ docs Cloudflare.

  },

Một isolate, nhiều request cùng lúc

Docs viết rõ: một instance Workers có thể xử lý nhiều request, kể cả request đồng thời, trên một vòng lặp sự kiện đơn luồng. Khi request A đang await (chờ mạng, chờ DO trả lời), isolate chạy request B. Không bao giờ có hai đoạn JavaScript chạy song song trong một isolate, nhưng các request đan xen nhau tại mỗi await. Vì thế biến cấp module là nơi dữ liệu của request này rò sang request khác:

let user;                                         // biến cấp module

export default {
  async fetch(req) {
    user = req.headers.get("x-user");             // A đặt "An"
    const data = await fetch("https://api.example/x");   // A chờ mạng → B chạy, đặt "Bình"
    return new Response("Xin chào " + user);      // A trả về "Xin chào Bình"  ← sai
  },
};

Quy tắc rút ra: dữ liệu của một request đi qua tham số hàm, không nằm trong biến cấp module. Hằng số chỉ đọc (danh sách route, bảng tra) thì để ngoài được. Worker của room engine không giữ gì: nó đọc URL, chọn phòng theo mã, chuyển tiếp.

Vòng đời một request và giới hạn

  • Request kết thúc khi bạn trả Response (hoặc khi stream body xong). Promise không được await có thể bị hủy giữa chừng.
  • Việc cần làm sau khi đã trả response thì đưa vào ctx.waitUntil(promise); có tối đa 30 giây sau khi response được gửi.
  • CPU mặc định 30 giây mỗi request trên gói Paid, nâng được tới 5 phút. Thời gian chờ mạng không tính là CPU.
  • 128 MB bộ nhớ mỗi isolate, dùng chung cho mọi request đang chạy trong isolate đó.

Bài 3Durable Object

Định nghĩa

Durable Object (DO) là một class JavaScript bạn viết và export từ Worker. Cloudflare tạo các object của class đó theo tên. Mỗi object có:

  • một tên (ID) duy nhất toàn cầu;
  • nhiều nhất một bản đang chạy tại một thời điểm, ở một địa điểm;
  • một storage SQLite riêng, nằm cùng máy;
  • các handler, được gọi khi có event.

Namespace, bindingenv.ROOMTập hợp mọi object của class Room. Worker gọi tới chúng qua binding này.
Tên, ID"K7QM2P"env.ROOM.getByName("K7QM2P") luôn trỏ tới cùng một object. Cách viết cũ hơn mà spec đang dùng: env.ROOM.get(env.ROOM.idFromName(code)). newUniqueId() tạo ID ngẫu nhiên; khi đó bạn phải tự lưu ID ở đâu đó.

src/index.js
import { DurableObject } from "cloudflare:workers";

export class Counter extends DurableObject {
  constructor(ctx, env) {
    super(ctx, env);                  // chạy khi object đang lạnh, không phải mỗi request
  }

  increment() {                       // method RPC, Worker gọi qua stub
    const n = (this.ctx.storage.kv.get("n") ?? 0) + 1;
    this.ctx.storage.kv.put("n", n);  // ghi bền, đồng bộ, không cần await
    return n;
  }
}

export default {
  async fetch(request, env) {
    const name = new URL(request.url).searchParams.get("room") ?? "lobby";
    const stub = env.COUNTER.getByName(name);    // cùng tên → cùng một object
    const n = await stub.increment();            // code này chạy BÊN TRONG object
    return new Response("Lượt thứ " + n + " của " + name);
  },
};

Cùng tên lobby thì mọi request, gửi từ Hà Nội hay Liège, đều tới đúng một object. Con số tăng 1, 2, 3… không trùng, không mất. So với biến hits ở bài 2: mỗi isolate có một hits riêng, nên con số đó vừa sai vừa biến mất khi isolate bị gỡ.

Mỗi tên đúng một bản, ở một nơi

  • Object được tạo gần nơi phát sinh request đầu tiên tới nó. Có thể gợi ý vùng bằng locationHint, nhưng đó chỉ là gợi ý.
  • Sau đó, mọi request cho tên này từ bất cứ đâu đều được chuyển tới đúng địa điểm đó. Người chơi ở xa phòng sẽ chịu độ trễ mạng cao hơn.
  • Một object xử lý được khoảng 500–1.000 request đơn giản mỗi giây. Vì vậy thiết kế chuẩn là một object cho mỗi đơn vị cần phối hợp (mỗi phòng), không dùng một object cho cả hệ thống.

Không có vòng lặp chính, chỉ có handler

Đây là câu trả lời cho câu hỏi "toàn bộ code chỉ là một hàm?". Một DO là một class có nhiều handler. Runtime gọi đúng handler khi event tới; giữa hai event, không có dòng code nào chạy.

Với object dùng SQLite, ctx.storage.kv.get/put/delete/list là API đồng bộ: trả giá trị ngay, không có Promise. Nhiều lệnh ghi liên tiếp không có await ở giữa được gộp lại và ghi nguyên tử.

Từng event một: input gate và output gate

Mỗi object chạy trên một luồng. Ngoài ra runtime có hai "cổng" để code dễ viết đúng:

Input gate
Trong lúc một thao tác storage đang chạy, không event mới nào được giao cho object. Ví dụ kinh điển: hai request cùng get("counter") rồi put(val + 1). Nhờ input gate, request thứ hai chỉ chạy tiếp sau khi request đầu xong, nên mỗi request nhận một số khác nhau.
Ngoại lệ
Chờ fetch() tới một dịch vụ ngoài thì không được che: event khác có thể chen vào trong lúc chờ.
Output gate
Trong lúc một lệnh ghi chưa bền, các tin gửi ra mạng (response, fetch mới) bị giữ lại; ghi lỗi thì tin bị hủy. Client không bao giờ thấy kết quả của một lần ghi chưa lưu. Docs không nói riêng về ws.send chưa kiểm chứng

Handler của room engine dùng API storage đồng bộ và chạy một mạch không có await, nên không event nào chen được vào giữa.

Bài 5Đường đi của một request HTTP

Ví dụ: An bấm "Tạo phòng" trong game cangua. Bấm "Tiếp" để xem từng bước: ô nào sáng là chỗ đang chạy code, dòng mono dưới mỗi ô là trạng thái của nó.

Ba điều rút ra

  1. Worker không giữ gì. Thông tin phòng nằm trong storage của Room DO; token nằm ở trình duyệt.
  2. Constructor chạy ở bước 5 chỉ vì object còn lạnh. Một request tới phòng này vài giây sau sẽ gọi thẳng method, không qua constructor.
  3. Request HTTP vào Worker tính là một request Worker. Mỗi lời gọi method qua stub tính là một request DO.
Worker · xử lý POST /cangua/api/create
async function create(request, env) {
  const { name } = await request.json();
  for (let i = 0; i < 3; i++) {
    const code = newCode();                                  // 6 ký tự ngẫu nhiên
    const r = await env.ROOM.getByName(code).create(name);   // RPC vào đúng phòng đó
    if (!r.err) return Response.json({ code, token: r.token, seat: r.seat });
  }                                                          // trùng mã thì thử mã khác
  return Response.json({ error: "BUSY" }, { status: 503 });
}

Bài 6Đường đi của WebSocket

Có token rồi, trình duyệt mở WebSocket. Đây là phần dễ hiểu nhầm nhất: Worker chỉ tham gia đúng một lần, lúc nâng cấp kết nối.

Code đầy đủ của đường WebSocket

Worker
if (url.pathname.startsWith("/cangua/ws/")) {
  if (request.headers.get("Upgrade") !== "websocket") return new Response(null, { status: 426 });
  const code = url.pathname.split("/").pop();
  return env.ROOM.getByName(code).fetch(request);   // trả nguyên response 101 của DO
}
Room DO
export class Room extends DurableObject {
  constructor(ctx, env) {
    super(ctx, env);
    ctx.setWebSocketAutoResponse(new WebSocketRequestResponsePair("ping", "pong"));
  }

  fetch(request) {                                  // chỉ chạy cho lần nâng cấp
    const [client, server] = Object.values(new WebSocketPair());
    this.ctx.acceptWebSocket(server);               // Hibernation API, không dùng server.accept()
    return new Response(null, { status: 101, webSocket: client });
  }

  webSocketMessage(ws, raw) {                       // mỗi tin của mọi người chơi trong phòng
    const msg = JSON.parse(raw);
    const room = (this.room ??= this.ctx.storage.kv.get("r"));   // RAM trống sau khi ngủ thì đọc lại
    // … kiểm tra, áp luật, this.ctx.storage.kv.put("r", room) …
    for (const s of this.ctx.getWebSockets()) s.send(JSON.stringify(viewFor(room, s)));
  }

  webSocketClose(ws, code, reason, wasClean) {
    // compat date từ 2026-04-07: runtime tự trả lời khung Close; trước đó phải gọi ws.close(code, reason)
  }
}

Vì sao WebSocket phải nằm ở DO

  • Worker thường cũng nâng cấp được WebSocket, nhưng không có trạng thái bền và không ngủ được. Isolate bị gỡ là kết nối mất.
  • Bốn người cùng phòng có thể rơi vào bốn isolate ở bốn nơi. Không isolate nào thấy socket của người khác để gửi cho cả phòng. Room DO là điểm hẹn duy nhất mà cả bốn socket cùng gắn vào.

Gắn một giá trị nhỏ (tối đa 16.384 byte) vào từng socket. Còn qua giấc ngủ, mất khi socket đóng. Room engine dùng nó để nhớ socket này là của người chơi nào; đọc lại bằng ws.deserializeAttachment().

acceptWebSocket(ws, ["p:an"]) rồi getWebSockets("p:an") để lọc. Tối đa 10 tag mỗi socket, mỗi tag tối đa 256 ký tự. Tag được truyền vào lúc accept.
getWebSockets(tag?)
Danh sách socket đang gắn với chính object này, còn nguyên sau khi ngủ dậy. Đây là cách gửi cho cả phòng.
setWebSocketAutoResponse
Edge tự trả lời một tin cố định (ví dụ "ping" → "pong") mà không đánh thức object và không tính duration.
getWebSocketAutoResponseTimestamp(ws)
Thời điểm gần nhất socket đó nhận auto-response, hoặc null. Dùng để đoán socket nào đã chết âm thầm.

Tính tiền và deploy

  • Lần nâng cấp: 1 request Worker và 1 request DO.
  • Tin gửi lên: không tính là request Worker; tính request DO theo tỉ lệ 20 tin bằng 1 request.
  • Tin gửi xuống, ping cấp giao thức và auto-response: miễn phí.
  • Deploy lúc phòng đang ngủ: lần thức kế tiếp chạy code mới, socket còn nguyên.
  • Deploy lúc phòng đang thức: docs mô tả cập nhật kiểu deferred (chờ object ngủ, có max_delay) và immediate. Khi bị ép cập nhật, socket bị ngắt; client phải tự kết nối lại và gửi lại hello. Storage còn nguyên. Chiến lược mặc định chưa kiểm chứng

Bài 8Alarm thay cho setTimeout

Đồng hồ lượt cần "đánh thức phòng vào giây thứ 60 dù không ai gửi gì". setTimeout làm được việc đó trong lúc object còn trong RAM, nhưng với giá rất đắt và không an toàn.

  • Alarm có thể kêu nhiều hơn một lần, nên alarm() phải idempotent: chạy lại cũng không làm hỏng gì.
  • Nếu object đang lạnh, constructor chạy trước alarm().
  • Room engine dùng một alarm duy nhất, đặt ở hạn sớm nhất. Client tự đếm ngược từ deadline trong state, nên server không phải gửi gì mỗi giây.
async afterWrite() {                                 // gọi (có await) sau mỗi lần ghi state
  const next = earliestDeadline(this.room);
  const cur = await this.ctx.storage.getAlarm();     // thao tác storage: input gate vẫn đóng
  if (cur === null || next < cur) this.ctx.storage.setAlarm(next);     // 1 dòng ghi, chỉ khi cần
}

async alarm() {                                      // có thể kêu trùng: phải idempotent
  const room = (this.room ??= this.ctx.storage.kv.get("r"));
  if (!room) return;                                 // phòng đã bị xóa
  // xử lý các hạn đã qua → ghi một lần → gửi state cho cả phòng → hẹn alarm kế tiếp
}

4 người, 60 nước đi, 10 lần hết giờ:

  • Request Worker: 4 lần tạo hoặc vào phòng + 4 lần nâng cấp = 8.
  • Request DO: 4 RPC + 4 nâng cấp + 64 tin gửi lên / 20 + 10 lần alarm ≈ 21.

  • Duration: mỗi event chạy vài mili giây, phần còn lại phòng ngủ: gần như bằng 0.

Edge
Các máy chủ Cloudflare gần người dùng, nơi nhận kết nối và chạy Worker.

Vùng cách ly V8 nơi code Worker chạy. Một tiến trình runtime chứa rất nhiều isolate.

Tên trong env trỏ tới một tài nguyên: env.ROOM là namespace của class Room.

Tập hợp mọi Durable Object của cùng một class.
Stub
Tay cầm để gọi một Durable Object cụ thể.
RPC
Gọi method của DO qua stub như gọi hàm: await stub.create(name).

Object bị gỡ khỏi RAM trong khi socket vẫn mở ở edge.
Attachment
Giá trị nhỏ gắn vào từng socket, còn qua giấc ngủ.
Input gate
Không giao event mới trong lúc một thao tác storage đang chạy.
Output gate
Giữ tin gửi ra cho tới khi lệnh ghi đã bền.

Hẹn giờ bền, mỗi object một cái, đánh thức object lúc tới hạn.
